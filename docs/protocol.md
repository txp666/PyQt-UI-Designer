## 一、数据流总览

```
┌──────────┐                                                    ┌──────────┐
│  下位机   │  ── 串口 / TCP / MQTT ──→  原始字节(raw)  ──→  解析器  │  上位机   │
│          │                                                    │          │
│          │              ┌─ serialRawReceived ──→ HEX字节提取模式           │
│          │  解析器输出 ──┤                                                │
│          │              └─ serialDataReceived ─→ 键值/JSON/MB            │
│          │                                                               │
│          │  ←── 所有已连接的链路 ←──  文本/HEX/Modbus帧  ←── 控件操作      │
└──────────┘                                                    └──────────┘
```

每条链路（串口、TCP、MQTT）都实现同一组信号，由 `CommHub` 汇总后发布；控件和绑定不区分数据来自哪条链路。信号名沿用 `serial` 前缀，含义适用于所有链路。

| 信号名 | 数据类型 | 说明 |
|--------|----------|------|
| `serialRawReceived` | `bytes` | 原始字节（串口读取、TCP 收到的数据、MQTT 消息载荷），供 HEX字节提取 使用；`hex` 模式的链路每次发一整帧，见[二、4](#4-二进制帧链路-hex-模式) |
| `serialDataReceived` | `dict` | 解析后的字典，供 键值匹配/JSON路径/Modbus 使用 |
| `serialDataSent` | `bytes` | 已发送的原始字节（用于调试回显） |
| `serialConnected` / `serialDisconnected` | `str` / 无 | 某条链路建立或断开，参数为链路描述，如 `COM3`、`TCP 192.168.1.10:8080`、`MQTT broker:1883` |
| `serialError` | `str` | 某条链路的错误信息 |

## 二、上行解析协议（接收）

### 1. 键值匹配

从解析后的字典中，用指定键名直接取值。

#### 参数

| 参数 | 类型 | 说明 |
|------|------|------|
| `key` | string | 字典键名 |
| `expression` | string (可选) | 转换表达式，如 `value * 0.1` |

#### 下位机发送格式（任选一种）

**格式A：KEY=VALUE（推荐简单场景）**

```
temperature=25.3,humidity=68.5\n
```

解析结果：`{"temperature": 25.3, "humidity": 68.5}`。键值分隔符设成 `:` 时写 `temperature:25.3,humidity:68.5`。

**格式B：JSON**

```json
{"temperature": 25.3, "humidity": 68.5}
```

解析结果：同上。JSON 不需要行结束符，可以跨多行、连着发，见[二、2](#2-json路径)。

**格式C：CSV（自动命名 ch0, ch1, ...）**

```
25.3,68.5,1013.2\n
```

解析结果：`{"ch0": 25.3, "ch1": 68.5, "ch2": 1013.2}`

**格式D：NMEA 语句（GPS、北斗、AIS 等）**

```
$GPGGA,123519,4807.038,N,01131.000,E,1,08,0.9,545.4,M,46.9,M,,*47\r\n
```

以 `$` 或 `!` 开头、以 `*HH`（两位十六进制，大小写都行）结尾的记录自动按 NMEA 校验：`$`（或 `!`）之后到 `*` 之前所有字节的异或等于 `HH` 才收下，不等就丢掉这条。收下的记录去掉开头的 `$` 和结尾的 `*HH`，再按普通记录解析，通常是 CSV，`ch0` 是语句名：

```python
{"ch0": "GPGGA", "ch1": 123519, "ch2": 4807.038, "ch3": "N", "ch4": 1131.0, "ch5": "E",
 "ch6": 1, "ch7": 8, "ch8": 0.9, "ch9": 545.4, "ch10": "M", "ch11": 46.9, "ch12": "M",
 "ch13": "", "ch14": ""}
```

`$*00` 这样去掉标记后为空的语句得到 `{"ch0": ""}`。以 `$` 开头但结尾没有 `*HH` 的记录不校验，照常解析，`$` 留在 `ch0` 里（`$GPTXT,hi` → `{"ch0": "$GPTXT", "ch1": "hi"}`）。

#### 记录格式（链路 `line` 模式的 `parserConfig`）

链路用 `line` 解析时，`parserConfig` 的这几个键决定一条记录怎么切、怎么读，都可以省略：

| 键 | 默认 | 说明 |
|----|------|------|
| `terminator` | `"\n"` | 行结束符，任意非空文字，如 `";"`、`"\r"`、`"\r\n"`、`"END"`。每条记录两端的空白（包括 `\r`、`\n`）都会去掉，空记录跳过，所以 `"\n"` 同时适用 `\r\n`；用 `"\r"` 时收到 `\r\n`，多出的 `\n` 成为下一条记录开头的空白，也被去掉 |
| `separator` | `","` | 字段分隔符 |
| `kvSeparator` | `"="` | 键值分隔符，`"="` 或 `":"`，只认这一个：`":"` 时 `temp:25.3,hum:60` 是键值，`temp=25` 整条按 CSV 成为 `ch0`；`"="` 时反过来。值里再出现分隔符不影响，`time:12:30` 得到 `{"time": "12:30"}` |
| `encoding` | `"utf-8"` | `"utf-8"`、`"gbk"` 或 `"ascii"`（大小写都行，文件里写小写）。整条记录按它解码，解不出的字节换成 `�`（U+FFFD）；`ascii` 下大于 0x7F 的字节都换成 `�`。`gbk` 下行结束符按 GBK 字节匹配，其他编码按 UTF-8 字节匹配 |

中文下位机常用 GBK 发中文键名：`温度=25` 的 GBK 字节是 `CE C2 B6 C8 3D 32 35 0A`，编码选 `gbk` 得到 `{"温度": 25}`，选 `utf-8` 键名会是乱码。

设计器里，没选中控件时的「默认帧格式」区和链路卡片的「帧格式」区，解析模式为 `line` 时有 分隔符、行结束符、键值分隔符、编码 四行。行结束符可以从下拉里选 `\n`、`\r\n`、`\r`、`;`，也可以直接输入，`\n` `\r` `\t` `\\` 按转义理解（输入 `\r\n` 就是回车换行，存进文件的是真正的回车换行符），其他反斜杠原样保留；清空时不保存。设置不合法时，打开工程、保存或连接时报错：`行结束符不能为空`、`键值分隔符只能是 = 或 :`、`编码只能是 utf-8、gbk 或 ascii`、`行分隔符不能为空`。

#### 完整示例

下位机（Arduino）：

```c
void loop() {
    float temp = readTemp();
    float humi = readHumi();
    // 格式A：KEY=VALUE
    Serial.print("temperature=");
    Serial.print(temp, 2);
    Serial.print(",humidity=");
    Serial.println(humi, 2);
    // 输出: temperature=25.30,humidity=68.50\n
    delay(1000);
}
```

上位机绑定设置：
- 解析模式：`键值匹配`
- 绑定字段：`temperature`

### 2. JSON路径

从解析后的嵌套 JSON 结构中，用点号分隔路径取值，支持数组下标。

#### 参数

| 参数 | 类型 | 说明 |
|------|------|------|
| `jsonPath` | string | 点号分隔路径，如 `data.sensors.0.temp` |
| `expression` | string (可选) | 转换表达式 |

#### 下位机发送格式

```json
{"data":{"sensors":[{"temp":25.3,"humi":68},{"temp":22.1,"humi":72}]}}\n
```

JSON 按括号分条，不靠行结束符：缓冲去掉开头的空白后以 `{` 或 `[` 开头时，括号配齐（字符串里的括号和 `\"` 这类转义不算；任一种右括号都算配上，`{"a":1]` 也算一条，只是解析失败被丢掉）就是一条消息，紧跟在后面的一个行结束符一起去掉。所以这些都能解析：

- **格式化的多行 JSON**：

  ```json
  {
    "data": {"sensors": [{"temp": 25.3, "humi": 68}]},
    "device": "ESP32"
  }
  ```

- **连着发、中间没有换行**：`{"temp":25.3}{"temp":25.4}` 是两条消息。
- **顶层数组**：变成键为 `"0"`、`"1"`……的字典。`[25.3, 60]` → `{"0": 25.3, "1": 60}`，键值匹配填键 `0`；`[{"temp": 25.3}, {"temp": 22.1}]` 用 JSON路径 `1.temp` 取 `22.1`。
- **JSON 后面紧跟的文字**是下一条普通记录：`{"a":1}xyz\n` 得到 `{"a": 1}` 和 `{"ch0": "xyz"}`。

括号配齐了但不是合法 JSON（如 `{"a":}`、`{"a": NaN}`），或者是空的 `{}`、`[]` 时，丢掉这条，后面的数据照常解析。以 `{` 或 `[` 开头的记录如果在字符串之外出现了 JSON 不可能有的字节（如 `=`），这一行丢掉，后面的记录照常解析。括号一直配不齐时会等下一次数据；一条消息超过 64 KiB 还没结束，丢到下一个行结束符（见[四](#四行协议自动识别规则)）。

#### 路径取值示例

| JSON路径 | 取得值 |
|----------|--------|
| `data.sensors.0.temp` | `25.3` |
| `data.sensors.1.humi` | `72` |
| `data.sensors.0` | `{"temp": 25.3, "humi": 68}` |

#### 完整示例

下位机（ESP32）：

```c
void loop() {
    StaticJsonDocument<256> doc;
    doc["device"] = "ESP32";
    JsonObject data = doc.createNestedObject("data");
    JsonArray sensors = data.createNestedArray("sensors");
    JsonObject s0 = sensors.createNestedObject();
    s0["temp"] = readTemp(0);
    s0["humi"] = readHumi(0);
    JsonObject s1 = sensors.createNestedObject();
    s1["temp"] = readTemp(1);
    s1["humi"] = readHumi(1);
    serializeJson(doc, Serial);
    Serial.println();  // 行结尾 \n
    delay(1000);
}
```

上位机绑定设置：
- 解析模式：`JSON路径`
- JSON路径：`data.sensors.0.temp`

### 3. HEX字节提取

直接从原始串口字节中，按固定偏移和数据类型提取数值。可选帧头帧尾定位有效载荷。链路用 `hex` 模式解析时，收到的原始字节就是完整的一帧，不填帧头帧尾、偏移从帧头第一个字节算即可，见[下一节](#4-二进制帧链路-hex-模式)。

#### 参数

| 参数 | 类型 | 说明 |
|------|------|------|
| `byteOffset` | int | 有效载荷内的字节偏移 |
| `dataType` | enum | `uint8` / `int8` / `uint16` / `int16` / `uint32` / `int32` / `float32` / `ASCII`* |
| `byteOrder` | enum | `大端(BE)` / `小端(LE)` |
| `frameHeader` | string | 帧头，十六进制字符串，如 `AA 55`（可选） |
| `frameTail` | string | 帧尾，十六进制字符串，如 `0D 0A`（可选） |
| `expression` | string (可选) | 转换表达式 |

> \* `ASCII` 类型仅数据绑定支持，曲线图不支持。

#### 帧结构

```
[帧头(可选)] [有效载荷] [帧尾(可选)]
```

解析时先找帧头位置，从帧头后开始；再找帧尾位置，帧尾前结束。得到的即为有效载荷，再按 `byteOffset` + `dataType` 提取。

#### 完整示例

**场景：传感器以固定帧格式发送温湿度**

帧格式定义：

```
帧头: AA 55
数据: [温度 float32 大端] [湿度 float32 大端]
帧尾: 0D 0A
```

下位机发送（C/STM32）：

```c
// STM32 是小端，memcpy 会得到 66 66 CA 41；这里按大端逐字节写入
static void put_float_be(uint8_t *dst, float v) {
    uint32_t u;
    memcpy(&u, &v, 4);
    dst[0] = u >> 24;
    dst[1] = u >> 16;
    dst[2] = u >> 8;
    dst[3] = u;
}

uint8_t frame[12];
frame[0] = 0xAA;           // 帧头
frame[1] = 0x55;
put_float_be(&frame[2], 25.3f);  // 偏移0: 温度 float32
put_float_be(&frame[6], 68.5f);  // 偏移4: 湿度 float32
frame[10] = 0x0D;          // 帧尾
frame[11] = 0x0A;
HAL_UART_Transmit(&huart1, frame, sizeof(frame), 100);
```

实际发送的十六进制：

```
AA 55 41 CA 66 66 42 89 00 00 0D 0A
```

上位机绑定设置（温度）：
- 解析模式：`HEX字节提取`
- 帧头(HEX)：`AA 55`
- 帧尾(HEX)：`0D 0A`
- 字节偏移：`0`
- 数据类型：`float32`
- 字节序：`大端(BE)`

上位机绑定设置（湿度）：
- 同上，字节偏移改为 `4`

#### 各数据类型字节长度

| 数据类型 | 字节数 | 范围 |
|----------|--------|------|
| `uint8` | 1 | 0 ~ 255 |
| `int8` | 1 | -128 ~ 127 |
| `uint16` | 2 | 0 ~ 65535 |
| `int16` | 2 | -32768 ~ 32767 |
| `uint32` | 4 | 0 ~ 4294967295 |
| `int32` | 4 | -2147483648 ~ 2147483647 |
| `float32` | 4 | IEEE 754 单精度浮点 |
| `ASCII` | 变长 | 到 0x00 或末尾（仅绑定） |

### 4. 二进制帧（链路 hex 模式）

链路的解析模式选 `hex` 时，链路自己从字节流里切出完整的帧、检查校验，再按字段表取出带名字的值，控件用 键值匹配 按字段名绑定即可。设置在属性面板里：没有选中控件时显示工程的「默认帧格式」（`.uidp` 的 `serial.parser` / `serial.parserConfig`，三种链路共用）；串口、TCP、MQTT 卡片的「默认解析模式」不是「项目设置」时，卡片属性下面多一个「帧格式」区，写到卡片自己的 `parserConfig`。卡片的 `parserConfig` 为空时，卡片模式和工程相同就沿用工程的设置，不同就用默认值。

#### 帧结构

```
[帧头] [长度字段 …] [数据] [校验] [帧尾]
```

除了数据，每一部分都可以没有。

#### 参数

| 参数 | 界面 | 默认 | 说明 |
|------|------|------|------|
| `header` | 帧头(HEX) | `"AA55"` | 帧头，HEX 文本，空格和大小写随意（`"AA 55"` 也行）；`""` 表示没有帧头 |
| `footer` | 帧尾(HEX) | `"55AA"` | 帧尾；`""` 表示没有帧尾 |
| `lengthOffset` | 长度字段偏移 | `-1` | 长度字段在帧内的偏移，从帧头的第一个字节算；`-1` 表示没有长度字段 |
| `lengthSize` | 长度字节数 | `1` | `1` 或 `2` |
| `lengthEndian` | 长度字节序 | `"大端(BE)"` | 2 字节长度的字节序，`"大端(BE)"` / `"小端(LE)"` |
| `lengthCovers` | 长度含义 | `"数据"` | 长度值数的是什么：`"数据"` / `"长度字段之后"` / `"整帧"`，见下 |
| `fixedLength` | 固定帧长 | `0` | 整帧字节数（含帧头、校验、帧尾），`0` 表示不固定；不能和长度字段同时用 |
| `checksum` | 校验 | `"无"` | `"无"` `"和校验"` `"异或"` `"CRC8"` `"CRC16-Modbus"` `"CRC16-CCITT"`，见下 |
| `checksumStart` | 校验起点 | `0` | 从帧内这个偏移开始算校验，算到校验字节的前一个字节 |
| `checksumEndian` | 校验字节序 | `"大端(BE)"` | 2 字节校验值在线路上的字节序；Modbus RTU 的 CRC 是 `"小端(LE)"` |
| `idleTimeout` | 空闲超时(ms) | `0` | 0–60000，`0` 表示不用，见「空闲分帧」 |
| `fields` | 字段表 | `[]` | 见「字段表」 |

所有键都可以不写；只有 `header`、`footer`、`fields` 的老工程照旧解析。帧尾、长度字段、固定帧长、空闲超时至少要有一个，否则不知道一帧在哪里结束，工程打不开并提示「HEX 帧需要帧尾、长度字段、固定帧长或空闲超时之一来分帧」。

#### 一帧在哪里结束

先找帧头，帧头前面的字节丢掉。然后按下面第一条配置了的规则定帧长：

1. **固定帧长**：帧长就是 `fixedLength`。
2. **长度字段**：收到长度字段后读出它的值 L，帧长按 `lengthCovers` 算：

   | `lengthCovers` | L 数的是 | 帧长 |
   |------|------|------|
   | `"数据"` | 长度字段之后、校验之前的数据 | `lengthOffset` + `lengthSize` + L + 校验字节数 + 帧尾长度 |
   | `"长度字段之后"` | 长度字段之后到帧末的全部字节 | `lengthOffset` + `lengthSize` + L |
   | `"整帧"` | 整帧，含帧头 | L |

   算出的帧长比长度字段、校验、帧尾加起来还短，比帧头短，或超过 65536 字节时，这不是帧。
3. **帧尾**：帧头之后第一次出现帧尾的地方。
4. **都没有**：等空闲超时，见下。

用固定帧长或长度字段定帧长、又设了帧尾时，帧末必须正好是帧尾。帧尾不对、校验不对、长度不合理时丢掉这一帧，从帧头的下一个字节起重新找帧头（没有帧头时往后挪一个字节），所以坏帧后面紧跟的好帧照常解析。数据里出现和帧头、帧尾一样的字节，不会截断用长度字段或固定帧长定长的帧，这正是长度字段的用处。

#### 校验

校验字节紧贴在帧尾前面，没有帧尾就在帧末。参与校验的是从 `checksumStart` 到校验字节前一个字节的这一段。

| 校验 | 字节数 | 算法 | `"123456789"` 的结果 |
|------|------|------|------|
| `和校验` | 1 | 所有字节相加，取低 8 位 | `0xDD` |
| `异或` | 1 | 所有字节异或 | `0x31` |
| `CRC8` | 1 | 多项式 0x07，初值 0x00，不反转，结果不异或 | `0xF4` |
| `CRC16-Modbus` | 2 | 多项式 0x8005 反转（0xA001），初值 0xFFFF，和 Modbus RTU 的 CRC 相同 | `0x4B37` |
| `CRC16-CCITT` | 2 | CRC-16/CCITT-FALSE：多项式 0x1021，初值 0xFFFF，不反转 | `0x29B1` |

2 字节的校验值按 `checksumEndian` 放到线路上，大端是高字节在前。

#### 空闲分帧

`idleTimeout` 大于 0 时，链路在这么多毫秒收不到新数据后结束当前的帧：

- 没有固定帧长、长度字段和帧尾时，帧头之后收到的全部字节就是一帧（没有帧头时就是收到的全部字节）；设了校验也照样检查。适合一包一包发、包和包之间有停顿的设备。
- 有其中任一规则时，到时还没凑齐的半帧丢掉，下一包从头开始，一次丢字节不会拖累后面的帧。

串口按读取时间判断空闲，TCP 每个连接各有一个定时器。MQTT 每条消息就是一次突发：设了空闲超时时，一条消息读完就结束这一帧；不设时半帧仍按主题留到下一条消息。

#### 字段表

`fields` 每项是 `[名字, 偏移, 长度, 类型]` 或 `[名字, 偏移, 长度, 类型, 字节序]`。偏移从**帧头之后的第一个字节**算（没有帧头就从帧首算）；字段能用的范围到校验字节 / 帧尾之前，超出范围的字段这一帧跳过。

| 类型 | 长度 | 结果 |
|------|------|------|
| `uint8` / `int8` | 1 | 整数 |
| `uint16` / `int16` | 2 | 整数 |
| `uint32` / `int32` | 4 | 整数 |
| `float32` | 4 | 小数 |
| `float64` | 8 | 小数 |
| `ASCII` | ≥ 1 | 到第一个 0x00 为止的文本 |
| `HEX` | ≥ 1 | 小写十六进制文本，如 `"0a1b"` |

定长类型的长度必须等于表里的字节数，类型名写错或长度不对时提示「无效 HEX 字段: 名字」。字节序 `"大端(BE)"`（默认）/ `"小端(LE)"` 只对多字节数值有意义。

属性面板的「字段表」一行写一个字段：`名字,偏移,长度,类型[,字节序]`，`#` 开头的行是注释，全角逗号也可以。有一行写错时，输入框下面提示「第 N 行格式错误」，改对之前保存的字段表不变。

#### 原始字节按帧发布

链路用 `hex` 模式时，`serialRawReceived` 每次发的是完整的一帧（帧头到帧尾），之后才是这一帧解析出的字典。所以 HEX字节提取 绑定和曲线的 HEX 模式不需要再填帧头帧尾，`byteOffset` 从帧头的第一个字节算；控件上填了帧头帧尾也照常工作（在这一帧里再定位一次）。`line` 和 Modbus 模式的链路仍按每次收到的字节块发布原始字节。

#### 完整示例

**场景：温湿度传感器发带长度字段和和校验的帧**

帧格式定义：

```
AA 55 | LEN | CMD | 温度 int16 小端 | 湿度 uint8 | SUM
LEN = CMD 到湿度的字节数（4），SUM = 从帧头起到湿度所有字节之和的低 8 位
```

下位机发送（C/STM32）：

```c
static void send_sample(uint8_t cmd, int16_t temp, uint8_t hum) {
    uint8_t frame[8];
    uint8_t sum = 0;
    frame[0] = 0xAA;                       // 帧头
    frame[1] = 0x55;
    frame[2] = 4;                          // LEN：后面 4 字节数据
    frame[3] = cmd;                        // 偏移1: CMD
    frame[4] = (uint16_t)temp & 0xFF;      // 偏移2: 温度 int16，小端
    frame[5] = (uint16_t)temp >> 8;
    frame[6] = hum;                        // 偏移4: 湿度 uint8
    for (int i = 0; i < 7; i++) {
        sum += frame[i];
    }
    frame[7] = sum;                        // 和校验
    HAL_UART_Transmit(&huart1, frame, sizeof(frame), 100);
}

send_sample(1, -10, 60);
```

实际发送的十六进制：

```
AA 55 04 01 F6 FF 3C 35
```

帧长 = 长度字段偏移 2 + 长度字节数 1 + L 4 + 校验 1 + 帧尾 0 = 8；和校验 = 0xAA+0x55+0x04+0x01+0xF6+0xFF+0x3C = 0x335，低 8 位是 0x35。

上位机设置（工程「默认帧格式」，或卡片的「帧格式」）：
- 解析模式：`hex`
- 帧头(HEX)：`AA55`；帧尾(HEX)：留空
- 长度字段偏移：`2`；长度字节数：`1`；长度含义：`数据`
- 校验：`和校验`；校验起点：`0`
- 字段表：

```
cmd,1,1,uint8
temp,2,2,int16,小端(LE)
hum,4,1,uint8
```

对应 `.uidp` 里的设置：

```json
"serial": {"parser": "hex", "parserConfig": {
  "header": "AA55", "footer": "", "lengthOffset": 2, "lengthSize": 1, "lengthCovers": "数据",
  "checksum": "和校验", "checksumStart": 0,
  "fields": [["cmd", 1, 1, "uint8"], ["temp", 2, 2, "int16", "小端(LE)"], ["hum", 4, 1, "uint8"]]}}
```

解析结果：`{"cmd": 1, "temp": -10, "hum": 60}`。字段偏移从帧头之后的 `04` 算：0 是 LEN，1 是 CMD，2–3 是温度，4 是湿度。绑定用 键值匹配，键填 `temp`、`hum`。

校验字节错了的帧（比如 `AA 55 04 01 F6 FF 3C 30`）整帧丢掉，紧跟着的 `AA 55 04 02 10 00 28 3D` 照常解析成 `{"cmd": 2, "temp": 16, "hum": 40}`；帧前面的杂乱字节跳过；一个字节一个字节到达，或两帧粘在一起到达，结果都一样。

要用 HEX字节提取 直接取温度：字节偏移 `4`（从帧头第一个字节 `AA` 算），数据类型 `int16`，字节序 `小端(LE)`，帧头帧尾不填。

### 5. Modbus（RTU / TCP / ASCII）

从 Modbus 响应帧解析出的字典中取寄存器/线圈值。

> **前提**：链路的解析模式需设置为 `modbus`（RTU，带 CRC）、`modbus_tcp`（MBAP 头，无 CRC）或 `modbus_ascii`（`:` 开头的十六进制文本，LRC 校验，见[五、Modbus ASCII](#modbus-ascii)），否则帧不会被解析为字典。三种解析器输出完全相同的字典，Modbus TCP 的单元标识符同样放在 `slave`，所以同一套绑定配置既能接串口 RTU / ASCII 设备，也能接以太网 Modbus TCP 设备。

#### 参数

| 参数 | 类型 | 说明 |
|------|------|------|
| `mbArea` | enum | 寄存器区：`响应内序号`（默认）/ `保持寄存器` / `输入寄存器` / `线圈` / `离散输入` |
| `regIndex` | int | `响应内序号` 时是响应里的第几个寄存器/线圈（从0开始）；选了寄存器区时是寄存器地址 |
| `mbDataType` | enum | `uint16` / `int16` / `uint32` / `int32` / `float32` |
| `mbRegOrder` | enum | `大端(AB CD)` / `小端(CD AB)`（双寄存器类型时有效） |
| `mbFcFilter` | int | 功能码过滤，`-1` 不过滤 |
| `mbSlaveFilter` | int | 从站地址过滤，`-1` 不过滤 |
| `expression` | string (可选) | 转换表达式 |

#### Modbus 解析器输出的字典格式

```python
# FC 0x03 读保持寄存器 - 响应
{
    "slave": 1,
    "fc": 3,
    "reg0": 1000,    # 第1个寄存器值 (uint16)
    "reg1": 2500,    # 第2个寄存器值
    "reg2": 100,     # 第3个寄存器值
}

# FC 0x01 读线圈 - 响应
{
    "slave": 1,
    "fc": 1,
    "coil0": 1,      # 第1个线圈 (0或1)
    "coil1": 0,
    "coil2": 1,
}
```

#### 各功能码响应的键

每个字典都有 `slave`（从站地址 / 单元标识符）和 `fc`（功能码，十进制数值），另外按功能码有：

| 功能码 | 响应 | 键 |
|--------|------|----|
| 0x01 / 0x02 | 读线圈 / 读离散输入 | `coil0`、`coil1`……；请求已知时加 `start` 和 `co{地址}` / `di{地址}` |
| 0x03 / 0x04 | 读保持寄存器 / 读输入寄存器 | `reg0`、`reg1`……；请求已知时加 `start` 和 `hr{地址}` / `ir{地址}` |
| 0x05 / 0x06 / 0x0F / 0x10 | 写线圈、写寄存器的回显 | `address`、`value`（0x0F / 0x10 的 `value` 是写入的数量） |
| 0x07 | 读异常状态 | `status`（1 字节） |
| 0x08 | 诊断 | `subfunction`、`data`（各 2 字节，大端） |
| 0x11（17） | 报告从站 ID | `id`（数据第 1 字节）、`run`（第 2 字节为 0xFF 时为 1，否则为 0）、`extra`（其余字节的小写 HEX 文本，没有时是空串） |
| 0x16（22） | 掩码写寄存器 | `address`、`andMask`、`orMask` |
| 0x17（23） | 读写多个寄存器 | 同 0x03：`reg0`、`reg1`……；请求已知时加 `start` 和 `hr{地址}`（读的那一段） |
| 功能码 + 0x80 | 异常响应（0x81–0x88、0x8F、0x90、0x91、0x96、0x97） | `error`（异常码）；请求已知时加 `start` |

0x07、0x08、0x11、0x16、0x17 只解析响应，控件和 Modbus 卡片不发这些请求；需要时用 HEX 模式手写请求帧。例如报告从站 ID 的响应 `11 11 05 0A FF 01 02 03 CRC_LO CRC_HI` 解析为 `{"slave": 17, "fc": 17, "id": 10, "run": 1, "extra": "010203"}`。

#### 按寄存器地址命名

Modbus 响应里没有起始地址，所以 `reg0`、`coil0` 是响应内的序号。解析模式为 `modbus`、`modbus_tcp` 或 `modbus_ascii` 的链路会记下自己发出的每条读请求（控件、Modbus 卡片发的，用 HEX 模式手写的请求帧也算；0x17 读写多个寄存器记下的是读的起始地址和数量），对上请求的响应字典里还会多出起始地址 `start` 和按寄存器地址命名的键：

| 功能码 | 寄存器区 | 键名 |
|--------|----------|------|
| 0x03、0x17 | 保持寄存器 | `hr{地址}`，如 `hr100` |
| 0x04 | 输入寄存器 | `ir{地址}` |
| 0x01 | 线圈 | `co{地址}` |
| 0x02 | 离散输入 | `di{地址}` |

```python
# 请求读从站1保持寄存器 200 起 4 个：01 03 00 C8 00 04 C5 F7
# 响应：01 03 08 0064 0000 41CA 6666 2F 99
{
    "slave": 1, "fc": 3,
    "reg0": 100, "reg1": 0, "reg2": 16842, "reg3": 26214,
    "start": 200,
    "hr200": 100, "hr201": 0, "hr202": 16842, "hr203": 26214,
}
```

响应与请求的对应关系：

- **Modbus TCP**：响应带回请求的事务标识符，按它找到请求，乱序回来的响应也不会错位。
- **Modbus RTU / ASCII**（包括走 TCP 的 RTU / ASCII 帧）：主站等到上一条的响应或超时才发下一条，所以响应对应同一从站、同一功能码的最近一次读请求，一条请求只对应一个响应。超时要设得比设备最慢的响应还长：超时后迟到的响应，会被当成下一条同从站、同功能码读请求的回复。
- 响应的寄存器数与请求不符，或者没有对应的请求（例如总线上另一个主站的请求、同一条请求的第二个响应）时，只有 `reg0` 这类序号键。
- 读线圈的响应按字节补齐到 8 位，`coil` 序号键包含补齐的位，`co` 地址键只包含实际读取的线圈。
- 异常响应找到请求时同样带 `start`。

#### 数据类型解析规则

| 数据类型 | 寄存器数 | 说明 |
|----------|----------|------|
| `uint16` | 1 | 直接取 `reg{i}` 无符号值 |
| `int16` | 1 | `reg{i}` > 32767 时减 65536 |
| `uint32` | 2 | 取 `reg{i}` 和 `reg{i+1}`，按寄存器序组合 |
| `int32` | 2 | 同上，有符号 |
| `float32` | 2 | 同上，IEEE 754 |

**寄存器序**说明：
- `大端(AB CD)`：`reg{i}` 为高16位，`reg{i+1}` 为低16位
- `小端(CD AB)`：`reg{i+1}` 为高16位，`reg{i}` 为低16位

#### 完整示例

**场景：读从站1的保持寄存器，地址0开始3个寄存器**

从站响应帧（十六进制）：

```
01 03 06 03E8 09C4 0064 CRC_LO CRC_HI
│  │  │  │    │    │
│  │  │  │    │    └─ reg2 = 0x0064 = 100
│  │  │  │    └────── reg1 = 0x09C4 = 2500
│  │  │  └─────────── reg0 = 0x03E8 = 1000
│  │  └────────────── 字节数 = 6
│  └───────────────── FC = 03 (读保持寄存器)
└──────────────────── 从站地址 = 1
```

解析结果字典：

```python
{"slave": 1, "fc": 3, "reg0": 1000, "reg1": 2500, "reg2": 100}
```

上位机绑定设置（读 reg0 作为温度，0.1倍）：
- 解析模式：`Modbus`
- 寄存器索引：`0`
- 数据类型：`uint16`
- 从站过滤：`1`
- 功能码过滤：`3`（或 `-1` 不过滤）
- 转换表达式：`value * 0.1`

**场景：PLC 的几块地址分别轮询，按寄存器地址绑定**

PLC 的数据常分散在几块地址里。按 `响应内序号` 绑定时，两块读请求的响应都从 `reg0` 开始编号，绑定分不清；按寄存器地址绑定就不会混：

- Modbus 卡片轮询表：`1,3,100,10`（保持寄存器 100–109）和 `1,3,200,4`（保持寄存器 200–203）
- 数值显示绑定保持寄存器 202 的 float32：寄存器区 `保持寄存器`、寄存器地址 `202`、数据类型 `float32`

32 位类型占地址和下一个地址两个寄存器，这两个寄存器要在同一次读取里。

**场景：读 float32（跨两个寄存器）**

从站寄存器 reg0=0x41CA, reg1=0x6666 → 组合 `41 CA 66 66` → float32 = 25.3

上位机绑定设置：
- 寄存器索引：`0`
- 数据类型：`float32`
- 寄存器序：`大端(AB CD)`

### 3. Modbus模式

自动构建标准 Modbus 请求帧，并按链路选择帧格式：解析模式为 `modbus_tcp` 的链路收到 Modbus TCP 请求（MBAP 头，事务标识符逐帧递增，无 CRC），解析模式为 `modbus_ascii` 的链路收到 Modbus ASCII 请求（`:`、大写十六进制、LRC、`\r\n`，见[五、Modbus ASCII](#modbus-ascii)），其余链路收到 Modbus RTU 请求（含 CRC16 校验）。控件只配置从站、功能码、地址和值，不需要区分 RTU、TCP 和 ASCII。

#### 参数

| 参数 | 类型 | 说明 |
|------|------|------|
| `mbSlave` | int (1-247) | 从站地址 |
| `mbFunc` | enum | 功能码（见下表） |
| `mbAddress` | int | 起始地址 |
| `mbValue` | int | 读取时=数量，写入时=值；只能是整数，int16 / int32 可以是负数，写小数用输入框 |
| `mbDataType` | enum | 写入值的类型：`uint16`（默认）/ `int16` / `uint32` / `int32` / `float32` |
| `mbRegOrder` | enum | 32 位类型的寄存器序：`大端(AB CD)`（默认）/ `小端(CD AB)` |

#### 支持的功能码

| 选项 | FC码 | 用途 |
|------|------|------|
| 01 读线圈 | 0x01 | 读离散输出 |
| 02 读离散输入 | 0x02 | 读离散输入 |
| 03 读保持寄存器 | 0x03 | 读保持寄存器 |
| 04 读输入寄存器 | 0x04 | 读输入寄存器 |
| 05 写单线圈 | 0x05 | 写单个线圈（ON=0xFF00, OFF=0x0000） |
| 06 写单寄存器 | 0x06 | 写单个保持寄存器；数据类型可选 `uint16` 或 `int16`（负数按补码写入） |
| 16 写多个寄存器 | 0x10 | 按数据类型写 1 个（16 位类型）或 2 个（32 位类型）保持寄存器 |

#### 帧格式

```
[从站地址 1B] [功能码 1B] [起始地址 2B 大端] [数量/值 2B 大端] [CRC16 2B 小端]
```

FC16 在地址后面是寄存器数、字节数和寄存器值：

```
[从站地址 1B] [0x10] [起始地址 2B 大端] [寄存器数 2B 大端] [字节数 1B] [寄存器值 N×2B 大端] [CRC16 2B 小端]
```

链路用 `modbus_ascii` 解析时，同样的字节（不含 CRC）写成 ASCII 帧，例如下面的读 3 个保持寄存器是 `:010300000003F9\r\n`。

#### 示例

**按钮轮询读取3个保持寄存器**

```
控件: PushButton
commandMode: Modbus
mbSlave: 1
mbFunc: 03 读保持寄存器
mbAddress: 0
mbValue: 3
```

点击 → 自动组帧：`01 03 00 00 00 03 05 CB`

分解：
```
01       从站地址 = 1
03       功能码 = 读保持寄存器
00 00    起始地址 = 0
00 03    数量 = 3
05 CB    CRC16
```

**开关控件写线圈**

```
控件: ToggleSwitch
commandMode: Modbus
mbSlave: 1
mbFunc: 05 写单线圈
mbAddress: 0
```

开关ON → `01 05 00 00 FF 00 8C 3A`
开关OFF → `01 05 00 00 00 00 CD CA`

**滑块写寄存器值**

```
控件: Slider (值 = 500)
commandMode: Modbus
mbSlave: 1
mbFunc: 06 写单寄存器
mbAddress: 10
sendOnChange: true
```

拖动到500 → `01 06 00 0A 01 F4 A9 DF`

分解：
```
01       从站地址 = 1
06       功能码 = 写单寄存器
00 0A    地址 = 10
01 F4    值 = 500
A9 DF    CRC16
```

**数值框写 float32 设定值**

```
控件: SpinBox (值 = 25)
commandMode: Modbus
mbSlave: 1
mbFunc: 16 写多个寄存器
mbAddress: 100
mbDataType: float32
```

改为 25 → `01 10 00 64 00 02 04 41 C8 00 00 61 B6`

分解：
```
01       从站地址 = 1
10       功能码 = 写多个寄存器
00 64    起始地址 = 100
00 02    寄存器数 = 2
04       字节数 = 4
41 C8    寄存器 100（float32 25.0 的高 16 位）
00 00    寄存器 101（低 16 位）
61 B6    CRC16
```

从站正常时回显地址和寄存器数：`01 10 00 64 00 02 00 17`。

#### Modbus 卡片：轮询表与响应超时

Modbus 卡片按"发送"发出界面上的一条请求，按"轮询"立即跑第一轮，之后每隔轮询间隔跑一轮。每条请求都等到响应或超时（`timeout`，默认 1000 ms）才发下一条，设备不回时不会在总线上堆积请求；上一轮没跑完时跳过这次轮询。

卡片靠解析后的响应判断设备回没回，所以至少要有一条已连接的链路用 `modbus`、`modbus_tcp` 或 `modbus_ascii` 解析。没有这样的链路时（比如用 `hex` 解析、靠 HEX 字节提取读原始字节），卡片认不出响应：轮询时每到间隔发一条，轮流发轮询表里的请求，不等回复，状态显示"已发送"。

卡片属性 `pollList` 是轮询表，每行一条读请求 `从站,功能码,地址,数量`，功能码只能是 1–4，`#` 开头的行是注释：

```
1,3,100,10
1,3,200,4
# 线圈
1,1,0,16
```

轮询表为空时，每轮发送界面上的那条请求。卡片状态显示结果：`设备已响应`、`无响应（1000 ms 超时）`、`设备返回异常 02 非法数据地址`；轮询时显示每一轮的结果，如 `轮询正常 · 3/3`、`第 2 条无响应 · 2/3`。

## 四、行协议自动识别规则

默认解析器为 `line` 模式，按缓冲扫描，每次取出一条消息：

- 先去掉缓冲开头的空白。以 `{` 或 `[` 开头时按括号配对取一个完整的 JSON 值（见[二、2](#2-json路径)），不需要行结束符；否则找行结束符（`terminator`，默认 `\n`，兼容 CRLF），找到就是一条记录，没找到就保留半包，不提前解析。
- 一批字节可能包含多条消息，解析器 `feed()` 返回按到达顺序排列的字典列表，读取线程逐条发送。
- JSON 字符串里的 `\n`、括号和转义不影响分条。括号配齐但解析失败的 JSON 会被丢弃，不再退回 CSV。
- 缓冲上限 64 KiB：取不出完整的消息、缓冲又超过这个长度时，丢到下一个行结束符（可能已经在缓冲里，比如没配齐的 `{` 后面）后恢复，避免持续噪声占满内存。
- HEX 帧解析器保留跨读取的半帧，按固定帧长、长度字段、帧尾或空闲超时切出整帧并检查校验，逐帧返回并限制缓存（见[二、4](#4-二进制帧链路-hex-模式)）；Modbus RTU 正常帧和异常帧都必须通过 CRC 校验；Modbus TCP 按 MBAP 的长度字段切帧，协议标识符不为 0 或长度与功能码不符的字节会被跳过；Modbus ASCII 按 `:` 和 `\r\n` 切帧，LRC 或长度不对的从下一个 `:` 重新找。
- HEX 字节绑定和曲线同时配置帧头、帧尾时，也会缓存半包并逐帧提取。未同时配置两个边界时按链路发布的原始单元提取：`hex` 模式的链路发布整帧，其他模式按每次读取的字节块，无法推断设备实际帧长；连续数据流应让链路用 `hex` 模式分帧，或在控件上配置明确的帧边界。

在串口、TCP 或 MQTT 配置卡片选择 `modbus` 才会使用 Modbus RTU 解析，选择 `modbus_tcp` 使用 Modbus TCP 解析，选择 `modbus_ascii` 使用 Modbus ASCII 解析；“项目设置”读取 `.uidp` 中的 `serial.parser` 和 `parserConfig`，三种链路共用这一份帧格式配置。这些选择同样适用于导出后的独立程序。

```
缓冲（去掉开头空白）
  │
  ├─ 以 '{' 或 '[' 开头？ ──是──→ 括号配齐 → JSON解析 → dict（数组 → 键 "0"、"1"…）
  │
  └─ 否 → 按行结束符(默认 \n)切出一条记录，两端去空白，按编码解码
       │
       ├─ 空记录 → 跳过
       │
       ├─ '$' 或 '!' 开头、'*HH' 结尾？ ──是──→ 异或校验：不对 → 丢弃；对 → 去掉 '$' 和 '*HH'
       │
       └─ 按分隔符(默认逗号)切分
            │
            ├─ 有键值分隔符(默认 '=') ？ ──是──→ KEY=VALUE模式
            │                    "a=1,b=2" → {"a": 1, "b": 2}
            │
            └─ 没有 ──────→ CSV模式
                               "1.0,2.0,3.0" → {"ch0": 1.0, "ch1": 2.0, "ch2": 3.0}
```

数值自动转换：整数优先(`int`)，否则浮点(`float`)，否则保留字符串。

## 五、Modbus 帧格式参考

### 请求帧（主站→从站）

**读请求 (FC 01-04)**

```
┌──────┬──────┬──────────┬──────────┬────────┐
│ 地址 │  FC  │ 起始地址 │   数量   │  CRC   │
│ 1B   │ 1B   │  2B BE   │  2B BE   │ 2B LE  │
└──────┴──────┴──────────┴──────────┴────────┘
```

**写单个 (FC 05/06)**

```
┌──────┬──────┬──────────┬──────────┬────────┐
│ 地址 │  FC  │ 寄存器/  │   值     │  CRC   │
│ 1B   │ 1B   │ 线圈地址 │  2B BE   │ 2B LE  │
│      │      │  2B BE   │          │        │
└──────┴──────┴──────────┴──────────┴────────┘
```

**写多个寄存器 (FC 16)**

```
┌──────┬──────┬──────────┬──────────┬────────┬──────────────┬────────┐
│ 地址 │ 0x10 │ 起始地址 │ 寄存器数 │ 字节数 │   寄存器值   │  CRC   │
│ 1B   │ 1B   │  2B BE   │  2B BE   │  1B    │  N×2B BE     │ 2B LE  │
└──────┴──────┴──────────┴──────────┴────────┴──────────────┴────────┘
```

### 响应帧（从站→主站）

**读响应 (FC 03/04)**

```
┌──────┬──────┬──────────┬──────────────────────┬────────┐
│ 地址 │  FC  │ 字节数   │    寄存器数据         │  CRC   │
│ 1B   │ 1B   │  1B      │  N×2B (每2B为大端值)  │ 2B LE  │
└──────┴──────┴──────────┴──────────────────────┴────────┘
```

**读线圈响应 (FC 01/02)**

```
┌──────┬──────┬──────────┬──────────────────────┬────────┐
│ 地址 │  FC  │ 字节数   │    线圈位数据         │  CRC   │
│ 1B   │ 1B   │  1B      │  N字节(每字节低位先)  │ 2B LE  │
└──────┴──────┴──────────┴──────────────────────┴────────┘
```

**异常响应**

```
┌──────┬──────────┬──────────┬────────┐
│ 地址 │ FC|0x80  │ 异常码   │  CRC   │
│ 1B   │  1B      │  1B      │ 2B LE  │
└──────┴──────────┴──────────┴────────┘
```

### CRC16 校验

采用 Modbus 标准 CRC16（多项式 0xA001），结果以**小端序**附加在帧末。

```python
def modbus_crc(data: bytes) -> int:
    crc = 0xFFFF
    for b in data:
        crc ^= b
        for _ in range(8):
            if crc & 1:
                crc = (crc >> 1) ^ 0xA001
            else:
                crc >>= 1
    return crc  # 低字节在前
```

### Modbus TCP（MBAP）

Modbus TCP 把同样的 PDU（功能码及其后的数据）放在 7 字节 MBAP 头之后，不再附加 CRC：

```
┌──────────┬──────────┬──────────┬────────┬──────────────────┐
│ 事务标识 │ 协议标识 │   长度   │ 单元ID │       PDU        │
│  2B BE   │ 2B = 0   │  2B BE   │  1B    │ 功能码 + 数据    │
└──────────┴──────────┴──────────┴────────┴──────────────────┘
```

长度字段 = 单元 ID 与 PDU 的字节数之和。读 3 个保持寄存器的请求与响应：

```
请求: 00 01 00 00 00 06 01 03 00 00 00 03
响应: 00 01 00 00 00 09 01 03 06 03 E8 09 C4 00 64
```

解析结果与 RTU 相同：`{"slave": 1, "fc": 3, "reg0": 1000, "reg1": 2500, "reg2": 100}`。上位机发出的请求事务标识符逐帧递增并在 65535 后回绕；响应带回的事务标识符用来找到对应的读请求，给寄存器加上地址键（见[二、5](#5-modbusrtu--tcp--ascii)）。

### Modbus ASCII

Modbus ASCII 把 RTU 帧去掉 CRC 后的每个字节写成两个十六进制字符（上位机发出的是大写），前面加 `:`，后面加两个字符的 LRC 和 `\r\n`：

```
┌─────┬──────────┬──────────┬──────────────┬──────────┬───────┐
│  :  │ 从站地址 │  功能码  │     数据     │   LRC    │ CR LF │
│ 1字符│  2字符   │  2字符   │   N×2字符    │  2字符   │ 2字符 │
└─────┴──────────┴──────────┴──────────────┴──────────┴───────┘
```

LRC = 从站地址到数据所有字节（按二进制值）求和，取二补码的低 8 位：

```python
def modbus_lrc(data: bytes) -> int:
    return -sum(data) & 0xFF
```

读从站 1 保持寄存器 0 起 1 个：

```
请求: :010300000001FB\r\n     01+03+00+00+00+01 = 0x05，LRC = 0x100-0x05 = 0xFB
响应: :010302000AF0\r\n       reg0 = 0x000A = 10，LRC = 0xF0
```

接收时先找 `:`，再找它后面的 `\r\n`；中间必须是偶数个十六进制字符（大小写都行）、LRC 正确、并且是一个长度对得上的响应，否则丢掉这个 `:`，从下一个 `:` 接着找。解析结果与 RTU 相同（`{"slave": 1, "fc": 3, "reg0": 10}`），响应和读请求也按 RTU 的规则对应：一问一答，同一从站、同一功能码的最近一条读请求只对应一个响应。

## 六、传输链路：串口、TCP、MQTT

三种链路都提供 `line`、`hex`、`modbus`、`modbus_tcp`、`modbus_ascii` 五种解析模式和"项目设置"选项，收到的数据走同一条解析、绑定和显示流程；按钮、开关、滑块等控件以及数据发送卡片、Modbus 卡片发出的命令，会发往**每一条已连接的链路**。导出的独立程序把三条链路放在 `comm_hub.py` 的 `CommHub` 里，`serial_handler.py`、`tcp_handler.py`、`mqtt_handler.py` 与设计器预览使用同一份实现。

### 1. 串口

串口配置卡片：端口、波特率、数据位、校验位、停止位、流控和解析模式。后台线程读取字节，按上面的规则切帧。

### 2. TCP

TCP 配置卡片：

| 参数 | 说明 |
|------|------|
| 模式 | `客户端`：上位机主动连接设备的 IP 和端口；`服务端`：上位机监听端口，等待设备连入 |
| 地址 | 客户端模式填设备 IP 或主机名；服务端模式填本机监听地址，`0.0.0.0` 表示所有网卡 |
| 端口 | 1–65535 |
| 解析模式 | 同串口 |

- 客户端连接是异步的：点击"连接"后显示"连接中"，成功后显示"已连接"，失败时在状态处显示原因（如连接被拒绝）。对方关闭连接会提示"TCP 连接已被对方关闭"并回到未连接状态。
- 服务端可同时接受多个设备连入，状态显示当前客户端数量。**每个连接独立切帧**，设备之间的半包不会互相干扰；命令会写给所有已连接的设备。HEX 字节提取绑定使用的是原始字节：`hex` 模式下是每个连接各自切出的整帧，不会混在一起；其他模式下是每次收到的字节块，多个设备同时发送时建议只接一个设备，或者改用 `hex` 模式、带键名的行文本 / JSON。
- TCP 是字节流，粘包、半包的处理和串口完全相同。
- `modbus_tcp` 解析模式对应标准 **Modbus TCP**（MBAP 头、无 CRC），此时控件和 Modbus 卡片发出的请求自动按 MBAP 组帧；`modbus` 解析模式对应 **Modbus RTU over TCP**（带 CRC 的 RTU 帧直接走 TCP），`modbus_ascii` 对应 ASCII 帧直接走 TCP。

### 3. MQTT

MQTT 配置卡片：

| 参数 | 说明 |
|------|------|
| 服务器 / 端口 | broker 地址和端口，默认 1883（TLS 常用 8883） |
| 客户端ID | 留空自动生成 |
| 用户名 / 密码 | 可选 |
| 订阅主题 | 一个或多个主题过滤器，用逗号、分号或换行分隔，支持 `+` 和 `#` |
| 发布主题 | 所有命令发布到这一个主题 |
| QoS | 订阅和发布共用，0/1/2 |
| TLS | 使用系统根证书校验 broker |
| 解析模式 | 同串口 |

MQTT 是消息流而不是字节流，解析规则有三点不同：

- **每条消息视为一帧**。行文本模式下，载荷不以行结束符结尾时自动补上配置的 `terminator`，`{"temp":25.3}`、`temp=25.3` 都可以直接发；HEX 帧模式按主题各自缓存半包，设了空闲超时时一条消息读完就结束这一帧。
- **纯数值载荷可按主题名绑定**。载荷只有一个值（如主题 `home/temp` 收到 `25.3`）时，解析结果同时给出 `ch0` 和主题名两个键：`{"ch0": 25.3, "home/temp": 25.3}`，绑定键填 `home/temp` 即可。带键名的行文本和 JSON 保持原样，不会附加主题。
- **命令原样发布**。命令内容以字节发布到发布主题；文本模式的"换行符"也会附在后面，发 MQTT 时一般把换行符设为"无"。

连接成功后才订阅主题；连接意外断开时会提示"正在重连"，卡片显示"重连中..."，paho 自动重连成功后再次显示"已连接"，订阅自动恢复。首次连接失败（地址错误、认证失败、TLS 证书不受信任）不会重试，修正后再点"连接"。TLS 通过操作系统的证书库（macOS 钥匙串、Windows 证书存储）校验服务器，打包后的程序也一样；自签证书的 broker 需要先把 CA 加入系统信任。

TCP 和 MQTT 卡片在"连接中"和"重连中"时都可以点"断开"取消。

### 4. 多条链路同时连接

串口、TCP、MQTT 可以同时连接。数据按到达顺序各自解析后进入同一套绑定；一条链路断开会清掉 HEX 绑定和曲线的半包缓存，其他链路继续工作。发送时，任一链路成功写入即视为发送成功，失败的链路通过错误信号提示。
